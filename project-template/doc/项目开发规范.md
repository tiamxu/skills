# 项目开发规范

## 一、目标

本规范用于约束后端项目的目录、分层、命名、路由、响应、错误处理、文档同步和修改流程。

核心原则：

- 分层清晰
- 命名一致
- 路由规范
- 响应统一
- 最小变更

## 二、技术栈与基础代码库规范

### 基础代码库

新项目优先基于指定基础代码库创建，不从零搭建。

使用基础代码库时必须保留：

- 原有目录结构
- 原有分层方式
- 原有配置方式
- 原有响应结构
- 原有错误处理方式
- 原有构建和启动方式

### 默认 Go 技术栈

| 能力 | 默认库 |
|---|---|
| 日志 | `github.com/tiamxu/kit/log` |
| HTTP 服务 | `github.com/tiamxu/kit/http` |
| 数据库 | `github.com/tiamxu/kit/sql` |

### 使用约定

- 启动阶段调用 `log.InitLogger`
- 程序退出前调用 `log.Sync`
- HTTP 服务默认使用 `kithttp.NewServer`
- 注册路由后调用 `srv.Start()` 启动监听
- 路由统一放在 `routes/`
- 数据库默认使用 `kit/sql`
- 数据库连接统一由 `repo.Init` 初始化
- repo 层使用 `kit/sql` 提供的 `*sql.DB`
- SQL 只允许写在 `repo/`
- 事务优先使用 `TransactCallback` 或 `TransactCallbackCtx`
- 查询无数据使用 `sql.IsNoRows` 判断

### 禁止项

- 未确认不得引入新的日志库
- 未确认不得引入新的 Web 框架
- 未确认不得引入 ORM
- 未确认不得绕过 `kit/sql` 重新封装数据库连接
- 禁止提交真实密钥、数据库密码、Token、第三方私密配置

## 三、目录规范

项目默认采用以下目录结构：

```text
api/            接口层，处理请求、参数校验、调用 service、返回响应
service/        业务逻辑层，处理业务规则、调用 repo
repo/           数据访问层，编写 SQL、访问数据库
routes/         路由定义
model/          数据库结构体，与数据表对应
types/          请求 / 响应结构体
middleware/     中间件
config/         配置加载
pkg/            公共包
doc/            项目文档
sql/            数据库脚本
```

目录职责必须稳定，不允许随意跨层调用。

## 四、分层规范

依赖方向只能从上到下：

```text
api -> service -> repo -> model
```

`types` 可被 `api` 和 `service` 使用。禁止 `repo` 反向依赖 `service` 或 `api`。

### api 层

职责：

- 解析请求参数
- 参数校验
- 调用 service
- 返回统一响应

禁止：

- 写业务逻辑
- 直接访问数据库
- 写 SQL
- 处理复杂数据组装

### service 层

职责：

- 编写业务逻辑
- 处理业务规则
- 调用 repo
- 组合业务数据
- 返回业务错误

禁止：

- 写 SQL
- 依赖 HTTP 框架上下文
- 直接处理接口响应

### repo 层

职责：

- 数据库查询
- SQL 编写
- 数据新增、修改、删除
- 返回数据库结果

禁止：

- 写业务逻辑
- 依赖 api / service
- 处理接口响应

### model 层

`model` 只表示数据库结构，与数据表字段对应。禁止混入请求参数或接口响应结构。

### types 层

`types` 只表示请求、响应、分页等接口结构。接口请求和响应优先使用 `types`，不直接把 `model` 作为请求参数。

## 五、命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| Handler | `XxxHandler` | `ProductHandler` |
| Service | `XxxService` | `ProductService` |
| 构造函数 | `NewXxxHandler()` / `NewXxxService()` | `NewProductService()` |
| 请求结构体 | `XxxReq` | `CreateProductReq` |
| 响应结构体 | `XxxResp` | `ProductDetailResp` |
| 列表响应 | `XxxListResp` | `ProductListResp` |
| 详情响应 | `XxxDetailResp` | `ProductDetailResp` |
| 文件命名 | 模块小写命名 | `api/product.go` |

Repo 函数按数据操作语义命名：

```go
CreateProduct()
GetProductByID()
GetProductList()
UpdateProduct()
DeleteProduct()
```

## 六、方法对应规范

同一业务动作在 `api / service / repo` 之间命名必须可追踪。

```text
新增：api.Create -> service.Create -> repo.CreateXxx
详情：api.Detail -> service.GetByID -> repo.GetXxxByID
列表：api.List -> service.GetList -> repo.GetXxxList
更新：api.Update -> service.Update -> repo.UpdateXxx
删除：api.Delete -> service.Delete -> repo.DeleteXxx
状态变更：api.UpdateStatus -> service.UpdateStatus -> repo.UpdateXxxStatus
批量操作：统一使用 BatchXxx
```

禁止同一动作在各层使用无关名称。

## 七、路由规范

路由统一放在 `routes/` 目录。

基础规则：

- 对外 API 推荐使用版本前缀，如 `/api/v1`
- 内部接口可按项目复杂度决定是否使用版本前缀
- 资源使用复数名词，如 `/api/v1/users`
- 单个资源使用 `:id`，如 `/api/v1/users/:id`
- CRUD 使用标准 HTTP Method
- 非 CRUD 动作放在资源 ID 后，如 `/api/v1/users/:id/disable`
- 认证接口放在 `/api/v1/auth`
- 管理端或内部接口按项目需要分组，如 `/api/v1/admin`、`/api/v1/internal`
- 禁止使用 `/getXxx`、`/createXxx` 这类动词式路径

CRUD 示例：

```text
GET    /api/v1/users
GET    /api/v1/users/:id
POST   /api/v1/users
PUT    /api/v1/users/:id
DELETE /api/v1/users/:id
```

动作接口示例：

```text
PUT  /api/v1/users/:id/disable
PUT  /api/v1/users/:id/enable
POST /api/v1/files/:id/restore
```

## 八、接口响应规范

所有接口统一使用 `Success` / `Error` 返回。只有 `api` 层允许处理 HTTP 响应，`service` 和 `repo` 不处理 HTTP 响应。

成功响应：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

失败响应：

```json
{
  "code": 400,
  "message": "参数错误",
  "data": null
}
```

分页响应：

```json
{
  "pageData": [],
  "total": 0,
  "pageNo": 1,
  "pageSize": 10
}
```

禁止每个接口自定义响应格式，禁止直接返回原始 `error`。

## 九、错误处理规范

错误码统一放在：

```text
pkg/e/
```

分层处理：

- `repo` 返回原始错误或包装后的底层错误
- `service` 转换为业务错误
- `api` 转换为统一响应

要求：

- 不忽略 `error`
- 不直接返回原始 `error`
- 不暴露 SQL 错误、数据库错误、堆栈信息
- 业务错误使用明确错误码
- 系统异常使用统一系统错误码

## 十、参数校验规范

`api` 层负责基础校验：

- 必填字段
- 类型校验
- 长度校验
- 枚举值校验
- ID 合法性校验

`service` 层负责业务校验：

- 数据是否存在
- 状态是否允许流转
- 用户是否有权限
- 库存是否足够
- 是否重复提交

禁止信任前端传入的数据。

## 十一、数据库规范

SQL 只允许出现在 `repo/`。

要求：

- 数据库连接统一由 `repo.Init` 初始化
- repo 层使用 `kit/sql` 提供的 `*sql.DB`
- 查询单条不存在时，推荐返回 `nil, nil`
- 查询列表为空时，返回空数组，不返回 `nil`
- 外部输入必须参数化，禁止字符串拼接 SQL
- 分页查询必须带 `limit` 和 `offset`
- 事务优先使用 `TransactCallback` 或 `TransactCallbackCtx`
- 查询无数据使用 `sql.IsNoRows` 判断

表结构变更必须提供：

- SQL 脚本
- 字段说明
- 默认值
- 是否允许为空
- 是否影响历史数据
- 是否需要数据迁移

## 十二、配置与安全规范

配置统一放在：

```text
config/
```

禁止硬编码：

- 数据库密码
- Token
- API Key
- 第三方密钥
- 私密配置

推荐按环境区分配置：

```text
config-dev.yaml
config-test.yaml
config-prod.yaml
```

## 十三、日志规范

应记录日志的场景：

- 服务启动失败
- 配置加载失败
- 数据库连接失败
- 第三方接口调用失败
- 关键业务异常

禁止打印：

- 密码
- Token
- API Key
- 支付密钥
- 用户敏感信息

## 十四、文档规范

以下变更必须同步 `doc/`：

- 新增或修改接口
- 修改请求字段
- 修改响应字段
- 修改错误码
- 修改核心业务流程
- 修改数据库结构
- 修改配置项

推荐文档：

```text
doc/设计文档.md
doc/接口文档.md
doc/错误码文档.md
doc/数据库变更记录.md
README.md
```

## 十五、依赖规范

默认禁止随意新增依赖。

新增依赖必须说明：

- 使用目的
- 是否已有替代方案
- 是否影响构建或部署
- 维护风险
- 安全风险

禁止为了少量代码引入大型框架。

## 十六、修改规范

简单修改可直接执行：

- 只涉及 1 个文件
- 需求明确
- 不改变接口
- 不改变数据结构
- 不影响核心流程

执行流程：

1. 修改代码
2. 执行必要测试
3. 输出修改说明
4. 如用户明确要求提交或推送，则测试通过后执行 `git commit` 和 `git push`

复杂修改必须先出方案，等待用户确认后再自动开发：

- 涉及多个模块
- 涉及 3 个及以上文件
- 修改接口协议
- 修改数据库结构
- 修改核心业务流程
- 引入新依赖
- 调整架构分层

方案必须包含：

- 修改目标
- 涉及文件
- 实现思路
- 影响范围
- 是否需要文档同步
- 是否需要联动修改
- 风险点

确认后的执行流程：

1. 修改代码
2. 更新必要文档
3. 执行自动化测试
4. 测试通过后执行 `git commit`
5. 执行 `git push`
6. 输出提交信息、推送结果、测试结果和影响范围

## 十七、自动化测试规范

修改 Go 代码后默认执行：

```bash
go test ./...
```

涉及依赖、生成代码或 `go.mod` 变化时执行：

```bash
go mod tidy
go test ./...
```

测试失败时：

- 必须优先定位并修复
- 不允许提交失败状态
- 如失败与本次修改无关，必须说明原因和影响范围

## 十八、Git 提交与推送规范

默认允许在用户明确要求提交或推送代码，或复杂任务方案确认后进入自动开发流程时执行 `git commit` 和 `git push`。

提交和推送前必须执行：

- `git status`
- `git diff`
- 项目测试命令，如 `go test ./...`
- 检查无密钥、Token、数据库密码等敏感信息
- 确认只包含本次任务相关修改

禁止：

- 测试失败时提交或推送
- 提交无关文件
- 未经单独确认执行部署
- 使用 `git reset --hard` 等破坏性 Git 命令

## 十九、最小变更原则

- 只改必要代码
- 不顺手重构
- 不调整无关格式
- 不修改无关模块
- 不扩大影响范围
- 不引入不必要抽象

## 二十、修改后输出规范

每次修改后必须说明：

- 修改文件列表
- 修改内容摘要
- 本次修改影响范围
- 是否兼容已有功能
- 是否需要联动修改
- 是否已更新文档
